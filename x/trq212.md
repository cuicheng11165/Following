### Opinions and takes

- 模型变聪明后需要更少指令与示例；示例会过度约束自由形式输出——应修剪上下文、多留运行空间。

- Opus 擅 coding，Fable 是更聪明的 generalist——基准测试不一定反映这一点。
- 手游成功更受局内经济与变现迭代约束；coding agent 可加速找对经济模型，但仍是真工作。
- 文件 harness 类工具长期可能消失（模型能力上升）。
- 「software engineering is the profession of automation」。

#### 1. **砍掉 ~80% system prompt：context engineering 长文**

**链接：** https://x.com/trq212/status/2080710971228918066  
**时间 / 互动：** 2026-07-24 · ❤️ 14785 · 🔁 1666 · 💬 393 · 🔖 30551 · 👁 ~3.8M  
**同步：** [Claude Blog](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)

##### 主帖在说什么

长文（X article）：用户消息只是上下文一小部分，真正决定结果的是 system prompt、Skills、CLAUDE.md、memory 等——即 **context engineering**。团队在 Opus 5 / Fable 5 上删掉 Claude Code system prompt **约 80%**，编码评测无明显损失。核心转变：少硬规则、多让模型判断；少示例、多设计工具接口；用 progressive disclosure 替代「一上来塞满」；工具说明放 description 而非重复写进 system prompt；记忆从 CLAUDE.md 热键转向 auto-memory；引用从简单 markdown 计划扩展到 HTML artifact、测试与 rubric。并推出 `/doctor`（claude doctor）帮用户精简 skills 与 CLAUDE.md。

##### 要点

- Context ≠ 单条 prompt；跨请求的通用 guidance 更难写
- 删 80% system prompt 无明显 coding eval 损失
- Then→Now：规则→判断；示例→接口设计；全塞→渐进披露；重复→工具描述；CLAUDE.md 记忆→auto-memory；简单 spec→富引用
- 实践：轻 CLAUDE.md 写 gotchas；skills 编码团队意见；优先代码/HTML/测试作 reference
- 工具：`/doctor` 自动 rightsize

#### 5. **手游成功：经济与变现，而非 one-shot 代码**

**链接：** https://x.com/trq212/status/2081214581301469668  
**时间 / 互动：** 2026-07-26 · ❤️ 107 · 🔁 1 · 💬 7 · 🔖 24 · 👁 ~13k  
**语境：** 回复 @signulll 关于「2012 年千万级手游如今可被 one-shot」的讨论。

##### 主帖在说什么

游戏早已 demand-constrained：手游成功主要取决于局内经济与变现，需要大量迭代测试。他认为 coding agent 可能让「找到正确经济模型」更快，但仍是实打实的工作。自跟补充：若自己做手游会设经济系统，让 Opus 跑 A/B、每天 brainstorm 并实现新策略——既是真工作，也更可能成功。

##### 要点

- 瓶颈在需求/经济/变现，不在写得出游戏
- Agent 加速的是经济实验循环
- 仍需人设局与持续迭代
- 反对「one-shot = 商业成功」的简化

##### 回复中的有价值观点

| 谁 | 观点 | 链接 |
|----|------|------|
